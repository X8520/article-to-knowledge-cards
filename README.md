# make-knowledge-cards

一个把文章或笔记转换成复习卡片的 Agent Skill。默认输出中文，支持直接粘贴的文本和本地 `.md` / `.txt` 文件。

## 1. 项目解决什么问题

长文章和笔记往往信息密集，逐段重读耗时；手动摘录又容易抓不住重点、重复记录，或者把原文没有的解释混进去。

`make-knowledge-cards` 把用户提供的文章拆成 5～8 个独立知识点，压缩成适合复习和背诵的卡片。每张卡片的内容都能追溯到原文，不靠扩写或常识补全。

## 2. 主要功能

- **生成 5～8 张知识卡片**：有效知识点不足 5 个时按实际数量输出；完全没有有效信息时直接返回固定提示。
- **固定四段结构**：每张卡片包含标题、核心知识、简明解释、自测问题/示例，卡片之间用 `---` 分隔。
- **一卡一点**：一张卡片只讲一个知识点，去除重复和近重复内容。
- **优先保留重点**：优先提取定义、结论、条件、机制和易错点，删除铺垫、口号、情绪化表达和空话。
- **严格依据原文**：不添加原文没有的事实、数字、名称或场景；自测问题也必须能仅凭原文回答。
- **语言可选**：默认中文；用户指定其他语言时，整张卡片使用该语言，并保持四段结构。
- **无额外依赖**：不需要安装脚本、插件或第三方服务，由运行它的 agent 提供模型能力。

## 3. 安装方法

将 `skills/make-knowledge-cards` 整个目录复制到你使用的 agent 的 skills 根目录：

- **Codex**：`~/.codex/skills/` 或项目内的 `.agents/skills/`
- **DeepSeek Harness**：项目内的 `.dsh/skills/`
- **其他支持 Agent Skills 的工具**：放入其约定的 skills 根目录

复制完成后，确认文件位于：

```text
<skills-root>/make-knowledge-cards/SKILL.md
```

目录结构如下：

```text
skills/make-knowledge-cards/
├── SKILL.md
└── agents/
    └── openai.yaml
```

`agents/openai.yaml` 提供 Codex 的展示名称、简短描述和默认提示词，不参与提取规则。安装不需要运行构建命令，也不需要安装额外依赖。

## 4. 使用方法

安装后直接提出任务，或显式点名技能。

**粘贴文章：**

```text
使用 make-knowledge-cards 把下面这篇文章整理成知识卡片：
<粘贴文章正文>
```

**读取本地文件：**

```text
读取 notes/http-cache.md，整理成知识卡片。
```

**指定语言：**

```text
Read notes/walking-meetings.txt and make six knowledge cards in English.
```

用户指定 5～8 之间的数量时，skill 会在原文信息足够的前提下按该数量输出；原文信息不足时仍以实际有效知识点为准。

支持的输入：

- 直接粘贴的文章、笔记或演讲稿
- 本地 `.md` 和 `.txt` 文件

暂不支持网页抓取、PDF、Anki 和图形界面。遇到网页或 PDF 时，需要先复制正文或另存为 `.md` / `.txt`。

## 5. 输入输出示例

### 输入

```markdown
# 写好 Git commit message 的五个要点

commit message 首先是给未来的维护者看的，不只是给自己看的。一条清楚的提交说明，能让人快速判断这次改动值不值得看、出了问题该回滚到哪里。

第一，标题行用一句话概括这次改动。不要写“更新”“修改”“修复问题”这类空话，它们没有说明改了什么。

第二，标题使用祈使句。例如写“修复登录超时问题”，而不是“修复了登录超时问题”。祈使句更像一条可执行的动作说明，也更适合被工具和团队统一使用。

第三，正文解释为什么改，而不是逐行复述代码改了什么。代码本身已经展示了“怎么改”，提交说明更该保留当时的背景、约束和取舍。

第四，一个 commit 只做一件事。把无关改动混在一起，会增加审查难度，也会让回滚变得困难。

第五，如果有关联的 issue，在正文中注明编号。这样后来的人可以从提交记录追溯到问题背景。
```

### 输出

````markdown
# 标题行用一句话概括改动
【核心知识】：commit 的标题行要用一句话概括这次改动。
【简明解释】：写“更新”“修改”“修复问题”这类空话没有说明改了什么，读者无法从标题看出改动内容。
【自测问题/示例】：标题行应该用什么方式概括这次改动？

---

# 标题使用祈使句
【核心知识】：commit 标题应使用祈使句。
【简明解释】：祈使句更像一条可执行的动作说明，也更适合被工具和团队统一使用。
【自测问题/示例】：标题写“修复登录超时问题”，而不是“修复了登录超时问题”。

---

# 正文解释为什么改
【核心知识】：commit 正文要解释为什么改，而不是逐行复述代码改了什么。
【简明解释】：代码本身已经展示了“怎么改”，正文更该保留当时的背景、约束和取舍。
【自测问题/示例】：提交说明的正文应该解释什么，而不是逐行复述代码？

---

# 一个 commit 只做一件事
【核心知识】：一个 commit 只做一件事。
【简明解释】：把无关改动混在一起，会增加审查难度，也会让回滚变得困难。
【自测问题/示例】：为什么一个 commit 只应做一件事？

---

# 正文注明关联 issue 编号
【核心知识】：如果有关联的 issue，要在 commit 正文中注明编号。
【简明解释】：注明编号后，后来的人可以从提交记录追溯到问题背景。
【自测问题/示例】：在正文注明关联 issue 的编号，能让后来的人从提交记录中做什么？
````

原文正好有 5 个有效知识点，因此输出 5 张。有效知识点更少时，不会为了凑满数量而扩写。

## 异常行为

| 情况 | 行为 |
| --- | --- |
| 有效知识点为 1～4 个 | 按实际数量输出，不补写、不道歉 |
| 没有任何有效信息 | 只回复 `无法提取有效知识点` |
| 文件无法读取 | 提示粘贴正文或提供可读取的 `.md` / `.txt` 文件 |
| 输入是网页、PDF、Anki 或图形界面 | 说明暂不支持，并给出受支持的输入方式 |

## 验证

已使用科普长文、技术文档、观点文、英文短文、营销软文、演讲稿和 Git 写作规范等样本进行测试，覆盖以下场景：

- 正常输出 5～8 张卡片；
- 有效知识点不足 5 个时不凑数；
- 英文原文在未指定语言时默认输出中文；
- 指定英文时，栏目标签同步本地化；
- 直接粘贴的文本和本地文件两条输入路径；
- 无有效信息时返回固定提示；
- 重复观点、数字引用和卡片分隔格式的校验。

Skill 已通过官方 `quick_validate.py` 校验，结果为 `Skill is valid!`。
